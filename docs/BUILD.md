# Building the firmware from source

This document explains how the binaries published in this repository are produced from upstream sources. A build is four inputs: the pinned mriscoc Marlin tree, configuration files generated by the mriscoc Special_Configurations configurator, a recorded set of hand edits on top of that generation, and one source patch without which the tree does not compile.

## Build inputs

| Component | Upstream | Pin / version |
| --- | --- | --- |
| Marlin tree | [mriscoc/Ender3V2S1](https://github.com/mriscoc/Ender3V2S1) | `ffe684b68bc5ce7d273079df4da7730065277e70` (2026-06-05) |
| Configurator | [mriscoc/Special_Configurations](https://github.com/mriscoc/Special_Configurations) | `0d422ac4425d12f7f0e1acf41f76ec308aa5b684` (2026-01-10) |
| Configurator scripts | `Configurator.pyw` v4.2 / `CreateConfigs.py` v6.2 | recorded in [Ender3S1-F1-UBL-IS-LA-MPC-BFT.ini](../configs/recipes/Ender3S1-F1-UBL-IS-LA-MPC-BFT.ini) |
| Marlin base | `bugfix-2.1.x` | reported as `2.1.4 MRiscoC` |

The build does not follow upstream HEAD. Both upstream trees are checked out at the pins above, so a rebuild reproduces the same source state rather than whatever the branches contain today.

## Repository and build layout

```text
Ender3S1Firmware/
├── configs/
│   ├── recipes/                       # per-variant recipe: generation call, hand edits, build env, result sizes
│   ├── Ender3S1-F1-v2/                # Configuration.h, Configuration_adv.h, Version.h, platformio.ini as compiled
│   ├── Ender3S1-F1-UBL-IS-LA-MPC-BFT/
│   ├── features/BFT.json              # custom configurator feature (binary file transfer)
│   └── patches/                       # 0001-machine-configs.patch, 0002-proui-add-ICON_ShapingZ.patch
├── firmware/                          # published binaries
├── logs/                              # build logs for the published binaries
├── scripts/                           # bootstrap.sh, build.sh, verify-artifacts.sh
└── docs/
```

Bootstrap creates the working tree at `build/`; it is not committed.

```text
build/
├── Ender3V2S1/                        # Marlin tree at the pinned commit
│   └── .pio/build/STM32F103RC_creality/
│       ├── firmware.elf
│       └── firmware-<date>-<time>.bin  # PlatformIO's timed output name
├── Special_Configurations/            # configurator at the pinned commit
├── .venv/                             # platformio==6.1.19
└── out/                               # build.sh copies the produced binary here
```

## Quick start

```bash
./scripts/bootstrap.sh Ender3S1-F1-v2
./scripts/build.sh Ender3S1-F1-v2
./scripts/verify-artifacts.sh
```

| Script | Behaviour |
| --- | --- |
| `./scripts/bootstrap.sh [variant]` | Clones the two pinned upstream repositories into `build/`, copies `configs/<variant>/` into the Marlin tree, applies the source patch `configs/patches/0002-proui-add-ICON_ShapingZ.patch`, and creates `build/.venv` with `platformio==6.1.19`. `variant` defaults to `Ender3S1-F1-v2`. |
| `./scripts/build.sh [variant]` | Runs the PlatformIO build and copies the produced `firmware-*.bin` to `build/out/<name>.bin`, printing flash and RAM usage. |
| `./scripts/verify-artifacts.sh` | Verifies the committed binaries against `firmware/SHA256SUMS` and checks the ARM vector table of each `.bin`. |

## Build procedure

### 1. Generate the configuration

The configurator is driven by a feature-selection list. The call for the current variant is:

```bash
cd build/Special_Configurations
python3 -c "import CreateConfigs; CreateConfigs.Generate('Ender3S1-F1-v2', ['Ender3S1','301F1','BLT','UBL','DACAI','T1','IS','LA','MPC','BFT'])"
```

| Selection | Effect |
| --- | --- |
| `Ender3S1` | printer profile: 220 × 220 mm bed, Sprite direct drive |
| `301F1` | `BOARD_CREALITY_V24S1_301`, environment `STM32F103RC_creality` |
| `BLT` | CR Touch on the BLTouch port |
| `UBL` | `AUTO_BED_LEVELING_UBL` |
| `DACAI` | `DACAI_DISPLAY` for the stock S1 color screen |
| `T1` | `TEMP_SENSOR_0 1` (stock thermistor) |
| `IS` | `INPUT_SHAPING_X`/`_Y` plus `SHAPING_MENU` (`M593`) |
| `LA` | `LIN_ADVANCE` (`M900 K`) |
| `MPC` | `MPCTEMP` with autotune and editing menus, replacing `PIDTEMP` |
| `BFT` | custom feature: re-enables `BINARY_FILE_TRANSFER` and `CUSTOM_FIRMWARE_UPLOAD` |

`BFT` is not a stock configurator feature. It is defined by [configs/features/BFT.json](../configs/features/BFT.json), installed into the configurator's `_features/` directory, and applied last in the list: the `301F1` board definition disables binary file transfer to save flash space, and the trailing `BFT` step undoes that.

The generated files are installed into the Marlin tree as plain copies:

```bash
cp build/Special_Configurations/Ender3S1-F1-v2/Configuration.h \
   build/Special_Configurations/Ender3S1-F1-v2/Configuration_adv.h \
   build/Special_Configurations/Ender3S1-F1-v2/Version.h \
   build/Ender3V2S1/Marlin/
```

The configurator also emits `platformio.ini`; the committed [platformio.ini](../configs/Ender3S1-F1-v2/platformio.ini) sets `default_envs = STM32F103RC_creality`.

### 2. Apply the hand edits

After generation, the following changes are made by hand. Line numbers are those recorded in the recipe and refer to the files as committed under [configs/Ender3S1-F1-v2/](../configs/Ender3S1-F1-v2).

| Setting | Location | Change |
| --- | --- | --- |
| `MPC_PTC` | `Configuration.h:757` | enabled (PTC heat-cartridge model, `alpha 0.0028` at 20 °C) |
| `MULTIPLE_PROBING` | `Configuration.h:1783` | set to `2` |
| `EXTRA_PROBING` | `Configuration.h:1784` | set to `1`; required companion, see note below |
| `GRID_MAX_POINTS_X` | `Configuration.h:2295` | `5` → `7` (UBL only; `GRID_MAX_POINTS_Y` derives from X on line 2296) |
| `SKEW_CORRECTION` | `Configuration.h:2462` | enabled (identity defaults, no-op until `M852`) |
| `SKEW_CORRECTION_GCODE` | `Configuration.h:2487` | enabled (`M852`) |
| `EEPROM_CHITCHAT` | `Configuration.h:2507` | disabled (trim step 1) |
| `EEPROM_INIT_NOW` | `Configuration.h:2511` | disabled (trim step 1) |
| `NOZZLE_CLEAN_FEATURE` | `Configuration.h:2627` | enabled (`G12`, default strokes and points) |
| `FAN_KICKSTART_TIME` | `Configuration_adv.h:624` | set to `100` ms |
| `INPUT_SHAPING_Z` | `Configuration_adv.h:1263` | enabled (`SHAPING_FREQ_Z 40.0`, `ZETA 0.15`; inert until `M593 Z` is set) |
| `EP_BABYSTEPPING` | `Configuration_adv.h:2376` | enabled (`EMERGENCY_PARSER` already on) |
| `SMOOTH_LIN_ADVANCE` | `Configuration_adv.h:2436` | enabled (`ADVANCE_TAU 0.02`); `ADVANCE_K` stays `0.0` |
| `NONLINEAR_EXTRUSION` | `Configuration_adv.h:2462` | enabled (`M592` coefficients default to 0, so no-op until set) |
| `BLOCK_BUFFER_SIZE` | `Configuration_adv.h:2737` | `16` → `32` |
| `BUFSIZE` | `Configuration_adv.h:2746` | `16` → `32` |
| `RX_BUFFER_SIZE` | `Configuration_adv.h:2765` | uncommented and set to `512` (`TX` stays 64) |
| `GCODE_MACROS` | `Configuration_adv.h:4152` | enabled (5 slots × 50 characters, `M810`–`M819`/`M820`) |
| `GCODE_MACROS_IN_EEPROM` | `Configuration_adv.h:4157` | enabled |
| `HOST_STATUS_NOTIFICATIONS` | `Configuration_adv.h:4297` | enabled |

`MULTIPLE_PROBING` and `EXTRA_PROBING` are a coupled pair: with `MULTIPLE_PROBING > 0`, `SanityCheck.h:1599` refuses to compile with the message "PROUI_EX requires an EXTRA_PROBING value of 1".

Configurations built for a specific machine additionally carry the calibration values (steps per unit, probe offsets, bed geometry, MPC model constants) that are visible in [0001-machine-configs.patch](../configs/patches/0001-machine-configs.patch).

### 3. Apply the source patch

One source fix is required and is independent of the configuration:

```c
// Marlin/src/lcd/dwin/proui/dwinui.h
#define ICON_ShapingZ  CI(1,ICON_MoveZ)
```

It is applied by [0002-proui-add-ICON_ShapingZ.patch](../configs/patches/0002-proui-add-ICON_ShapingZ.patch), and it goes next to the existing `ICON_ShapingX`/`ICON_ShapingY` aliases. With `INPUT_SHAPING_Z` and `SHAPING_MENU` both enabled, `proui/dwin.cpp` references `ICON_ShapingZ` in `drawInputShaping_menu()`, but upstream defines only the X and Y aliases, so the build fails. Keep the line when pulling future mriscoc updates, or verify that upstream has fixed it.

### 4. Compile

```bash
cd build/Ender3V2S1
../.venv/bin/platformio run -e STM32F103RC_creality
```

This is the command `build.sh` wraps. A clean build of the current variant takes 43.57 s and reports success for `STM32F103RC_creality`.

## Flash and RAM budget

| Metric | Value |
| --- | --- |
| Flash used | 232344 B of 233472 B (99.5%, 1128 B free) |
| RAM used | 28064 B of 49152 B (57.1%) |
| Build time | 43.57 s |
| Compiler warnings | none in the final build log |
| Binary on disk | 232972 B (includes padding; flash usage is 232344 B) |
| MD5 of the published binary | `6e11c30095187fd50a62fa75904379f0` |

The flash is 256 KiB, but the application does not start at `0x08000000`:

| Region | Address range | Size |
| --- | --- | --- |
| Stock bootloader (not written by this build) | `0x08000000`–`0x08006FFF` | 28 KiB |
| Application, this firmware | `0x08007000`–`0x0803FFFF` | 228 KiB (233472 B) |
| End of flash | `0x08040000` | 256 KiB total |

So the buildable budget is 256 KiB − 28 KiB = 228 KiB = 233472 B. With 1128 B free, the current configuration is effectively full: any new feature needs a trim first.

### Trimming when a feature does not fit

Apply the steps in order and stop as soon as the link fits.

| Step | Change | Flash saved |
| --- | --- | --- |
| 1 | Disable `EEPROM_CHITCHAT` and `EEPROM_INIT_NOW` | 444 B (measured in this tree) |
| 2 | Disable `PRINTCOUNTER` | ~0.9 KiB |
| 3 | Disable the colors menu | ~1.2 KiB |
| 4 | Disable `plot` | ~0.8 KiB |
| 5 | Disable ESDiag and the lockscreen | ~0.8 KiB |
| 6 | Replace `PIDTEMPBED` with bang-bang bed control | ~2 KiB |

Step 1 was applied to the current variant; the first link of this configuration overflowed by 444 B and those two options recovered it. `SKEW_CORRECTION` was deliberately kept. Step 6 changes bed behaviour and should be treated as a last resort, not a pure size change.

## Rejected and known-bad options

| Option | Reason |
| --- | --- |
| `FT_MOTION` | the STM32F103 has no FPU |
| `-flto` | produces a binary that fails to boot (mriscoc issue #1083) |
| `S_CURVE_ACCELERATION` | conflicts with junction deviation, which this build uses |
| `SDCARD_READONLY` | disables the SD write path that binary file transfer depends on |

## Known failure modes

| Symptom | Cause | Resolution |
| --- | --- | --- |
| Sanity check: "PROUI_EX requires an EXTRA_PROBING value of 1" | `MULTIPLE_PROBING 2` set without `EXTRA_PROBING 1` | set `EXTRA_PROBING 1` (`Configuration.h:1784`) |
| Compile error: `ICON_ShapingZ` undeclared in `proui/dwin.cpp` | `INPUT_SHAPING_Z` + `SHAPING_MENU` enabled, alias missing upstream | apply [0002-proui-add-ICON_ShapingZ.patch](../configs/patches/0002-proui-add-ICON_ShapingZ.patch) |
| Link overflow of a few hundred bytes | configuration grew past 233472 B | work through the trim ladder above |

Both failures occurred while producing the current variant, which is why the recipe records it as the third attempt.

## Verifying the build

### M115

After flashing, query the printer over serial (250000 baud):

```gcode
M115
```

The response must contain `Ender3S1-F1-v2` and the build date. If the machine name is missing or wrong, a different binary was flashed — the stock bootloader silently skips SD filenames it has already seen, so use a filename that has never been used on that card.

Because the EEPROM layout changed (`GCODE_MACROS_IN_EEPROM` adds macro slots), run `M502` followed by `M500` after flashing rather than relying on the previous settings.

### Committed binaries

```bash
./scripts/verify-artifacts.sh
```

The script checks each committed binary against `firmware/SHA256SUMS` and validates its ARM vector table, which catches a truncated or wrongly based image.

A manual check of the vector table reads the first two words of the `.bin`: the initial stack pointer must fall inside the 48 KiB RAM at `0x20000000`, and the reset vector must fall inside the application region starting at `0x08007000`. In the published binary `SP=0x2000BFD8` and the reset vector is `0x080092C5`; all 63 exception/IRQ slots are present, every populated one points into the application region (highest `0x0800DD5C`) and the unused slots are zero. This is the same layout as the previous variant, which uses the same `0x7000` bootloader offset.

### Reproducibility

Measured on 2026-10-27: bootstrap plus build from the pinned commits, compared against the published image, differed in 16 bytes only - the two embedded build-stamp strings (`Jul 30 2026 16:04:49` versus `Oct 27 2026 14:41:40`). File size (232972 B), flash usage (232344 B), RAM usage (28064 B) and the reset vector (`0x080092C5`) matched exactly.

Two builds of the same source and configuration are never byte-identical. [Version.h](../configs/Ender3S1-F1-v2/Version.h) sets `STRING_DISTRIBUTION_DATE` to `__DATE__` and `STRING_DISTRIBUTION_TIME` to `__TIME__`, so the build timestamp is compiled into the image. Compare flash usage (232344 B, 99.5%) and the `M115` output instead of hashes. A hash comparison is only meaningful for the exact published file.

## Why the configuration files are committed instead of only a recipe

The recipe records the configurator call and every hand edit, so the generation step is reproducible. But the configurator is a code generator: its output depends on its own version and on the set of feature JSON files present, and any of those can change independently of the recipe. The committed [Configuration.h](../configs/Ender3S1-F1-v2/Configuration.h), [Configuration_adv.h](../configs/Ender3S1-F1-v2/Configuration_adv.h) and [Version.h](../configs/Ender3S1-F1-v2/Version.h) are the exact byte-for-byte input to the shipped binary. Keeping them means a reader can diff a fresh generation against what was actually compiled — which is how the no-drift check between the two variants was performed — without having to reconstruct the generator state first. The recipe explains intent; the headers are the artifact.
